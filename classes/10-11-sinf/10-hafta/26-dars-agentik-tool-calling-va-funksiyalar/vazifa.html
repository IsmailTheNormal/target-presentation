1-Bosqich: Baza 4 BALL

send_email Vositasi Uchun JSON Schema Yozish

Elektron pochta yuboruvchi send_email vositasi uchun JSON Schema spetsifikatsiyasini yozing. to, subject va body maydonlari majburiy (required) bo'lsin:

// Kutilayotgan JSON Schema strukturasi: { "name": "send_email", "description": "Foydalanuvchiga elektron xat yuborish", "parameters": { "type": "object", "properties": { ... }, "required": [ ... ] } }

✅ Etalon JSON Schema

{
  "name": "send_email",
  "description": "Yangi elektron xabar jo'natish",
  "parameters": {
    "type": "object",
    "properties": {
      "to": { "type": "string", "description": "Qabul qiluvchi email manzili" },
      "subject": { "type": "string", "description": "Xat mavzusi" },
      "body": { "type": "string", "description": "Xatning asosiy matni" }
    },
    "required": ["to", "subject", "body"]
  }
}
2-Bosqich: Amaliyot 4 BALL

Xatolarni Observation ga Qaytarish Mexanizmi

Nega tashqi vosita xato berganda (masalan API ishlamasa yoki baza topilmasa) butun agent jarayoni to'xtatilmay, balki xato matni modelga qaytarilishi kerak? Ushbu ReAct muhandislik tamoyilini tushuntiring:

✅ Observation Loop Arxitekturasi

Agar server qulasa, butun sessiya yo'qoladi. Agar xato Observation ga { error: true, message: "..." } shaklida qaytarilsa, til modeli keyingi Thought bosqichida xatoni o'qib, boshqa parametr yoki muqobil vosita orqali o'zini o'zi tuzatadi (Self-healing agent).

3-Bosqich: Kiber-Chaqiruv 2 BALL

Kiber-Chaqiruv: RCE Mudofaasi va Sandboxing

Agentga to'g'ridan-to'g'ri xom eval() yoki erkin bash buyruqlari berilsa, qanday kiber-xavflar yuzaga keladi? Buning oldini oluvchi 3 ta Sandboxing qoidasini yozing:

✅ Sandboxing 3 Oltin Qoidasi

  1. Xom va ochiq shell mutlaqo taqiqlanadi (RCE butun serverni yo'q qiladi).
  2. Faqat ruxsat berilgan asboblar oq ro'yxati (Whitelist) va Zod validatsiyasi.
  3. Root huquqlarisiz Docker konteynerida izolyatsiya va ichki tarmoqdan uzish.
